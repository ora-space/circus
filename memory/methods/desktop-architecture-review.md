# desktop PR 架构原则检查

本文定义 desktop 仓库 PR 的架构审查原则，并要求以当前实现证明符合性。审查重点是同一事实是否只有一个手写来源、职责是否由正确的模块拥有，而不是改动文件少或自动检查全绿。本方法不替代 PR 本身的需求与行为正确性检查。

## 审查依据与核心原则

架构原则的审查依据是 desktop 仓库当前的 `docs/feature-change-guide.zh.md` 和本文原则。指南规定具体接入方式，本文帮助判断职责与行为；两者发生冲突时以当前指南为准并指出差异。无需读取历史重构方案、验收记录或某次任务的临时产物，也不要求生成临时文件清单。

1. **单一事实来源**：同一语义只在所属模块手写一次，其余表示由声明派生。判断重复看是否需要人工同步，而不是文件数或文本是否相似；不同协议边界可以有各自独立的事实。
2. **完整职责所有权**：领域接口封装完成用例所需的规则、状态变化、失败处理和协调。调用方表达意图，不应了解内部存储、锁或重新拼装领域策略；公共基础设施统一拥有请求与 stream 的通用生命周期。
3. **最小公共接口**：公开能力由真实跨边界需求决定，暴露用例而非内部机制。声明了 purpose、通过访问检查或在 TypeScript 中 export，都不能单独证明需要公共授权。
4. **显式且必要的组合**：组合根连接已有所有者，业务规则留在所有者内。新领域的装配是合理改动；实际共享需求才支持提取新抽象，不为假想扩展增加通用容器或重新建立根业务 facade。
5. **生命周期闭环与隔离**：创建资源就要明确停止和释放责任；成功、失败、取消、范围切换和关闭都保持状态一致。完成信号对应承诺的完成阶段，一个 workspace 的更新或清理不得污染另一个。
6. **行为证据与声明检查分层**：生成和静态门禁证明声明一致性，真实接口测试证明调用与行为，宿主测试证明装配。通过某一层不能替代另一层，测试替身应位于类型化依赖边界而非替换被测生产实现。
7. **变更与删除同样完整**：添加时让规则归位，删除时收回专属接口、接线和状态，同时保留共享职责与用户持久数据。测试义务随存活职责迁移，不能因文件移走而丢失。

## 1. 确认 PR 范围并阅读实现

- 确认评审的 base/head 与未提交修改边界，代码证据对应同一版本；PR 更新后复核受影响结论。
- 通过 PR diff 定位变化，再阅读完整实现和实际消费者，包括相关的未改动调用方；对删除和重命名检查旧引用与残留。
- 按所有者实现／声明、必要组合、生成产物、测试、文档分类理解改动。对每个受影响的用例应用下述相关检查，明确未覆盖范围；工具和中间产物按任务需要选择。

完成条件：PR 的行为变化、受影响所有者和消费链明确，结论对应实际评审版本。

## 2. 沿操作链核对四项手写事实

对每个新增或变更的集成操作，追踪“契约 → 逻辑操作 → Desktop 绑定 → 业务实现 → 消费者”，对照当前指南核对：

| 手写事实 | 审查问题 |
|---|---|
| 契约 | DTO 及其导出是否由契约所有者定义？公共 DTO／manifest 是否混入 transport 路由或 Webview 授权？ |
| 逻辑操作 | 名称、命名空间／成员、DTO 引用和 unary/stream 模式是否来自逻辑 catalog？是否又引入按名称猜模式的回退？ |
| Desktop 绑定 | handler、权限和 stream 启动接线是否属于 Desktop catalog？无 SDK 对应的 native command 是否也纳入？主 Webview 与 plugin Webview 的权限是否分别审查？ |
| 业务实现 | 是否经窄领域句柄执行？宿主 adapter 是否复用请求生命周期？是否重新出现根 Backend 业务转发、内部存储／锁泄露或重复 stream 注册、取消、结算逻辑？ |

确认客户端转发、DTO barrel、transport map、stream dispatch、command 注册及权限产物来自声明生成，而非人工维护平行表。审查生成器变化时，同时核对生成内容和错误检测能力。

“四项事实”不是“四个文件”，也不是禁止其他手写代码：测试、文档、公共接口政策、新领域的必要组合和宿主原生能力各有职责。对 native event 等不在 SDK 操作链内的通道，单独核对 payload、事件名和消费的一致性来源；两端手写类型加泛型监听不等于跨语言校验。先辨明协议边界，不机械要求一切进入 SDK stream，也不把 Controller–Node 的独立协议算作重复 Desktop 路由。

完成条件：每个操作的声明来源与消费链明确；每个额外手写接线点都能解释其独立职责，而非维护同一事实的另一份副本。

## 3. 检查公共接口与数据所有权

- **`interface.json`**：逐一搜索新增或变化符号的实际跨 feature 消费者，核对 purpose 和所需能力。仅同一 feature 内部／内部测试使用的 TypeScript export 不需要公共授权；有真实共享职责的接口保留。检查器允许访问只能证明符合声明，不能证明声明本身合理，尤其注意为绕过边界检查而扩大公开面。
- **数据**：query 身份、权威响应采用、失效及删除级联由数据所有者负责。检查 UI 是否复制 query key 或自行拼装领域缓存策略；沿 mutation、手动刷新、Agent／native event 等所有入口核对相关查询是否一起更新，以及 pending 是否等待应当完成的刷新。用具体场景说明不一致后果，不将“依赖 watcher”直接等同于“永远不会刷新”。
- **资源与组合**：翻译按职责归属，保留单一同步 i18n 初始化；判断资源所有者而非仅看 key 前缀。Files 保留明确的 Explorer／Search 组合；新容器、根 facade 或通用框架需要真实跨域需求，局部 context 或必要依赖注入本身不是违规。

完成条件：每个扩大公开面的符号有消费者与职责依据；变更数据的入口使用明确的领域策略，并保持 workspace／scope 隔离。

## 4. 沿生命周期和测试验证行为

- 对 watcher、事件桥、timer、QueryClient observer、stream、native surface，确认谁创建、谁持有、谁停止；覆盖 scope 切换、卸载／关闭、启动中取消和失败路径。区分取消信号发出、清理触发、清理完成，证据只能支持实际观察到的阶段。
- 前端从真实组件、hook 或操作接口进入生产客户端，以类型化 handler 配置响应。显式组合 memory adapter；未配置操作失败，空成功只用于测试明确选择的合成行为。按钮 callback、替换客户端方法或“返回 iterable”不能替代集成行为证据。
- 按变更风险核对 DTO、call-option、错误／requestId、异步刷新、缓存隔离与资源终结。Stream 要有实际消费、abort／卸载及清理证据；Backend 在行为依赖 SQLite／Git 时保留真实依赖。分清领域测试、请求执行器测试与宿主装配测试各自证明什么。
- 删除功能时追踪共享消费者、缓存／草稿归属及旧符号残留；保留其他 workspace 和其他所有者仍需要的状态、query factory 与失效策略。产品删除不授权删除用户文件，文件系统布局仍按硬兼容边界处理。

完成条件：每条关键变化有相应行为证据；缺失的测试与已复现的运行错误分别报告。

## 5. 运行门禁并给出可追溯结论

- 从当前 Taskfile／xtask 确认命令和覆盖范围，按改动运行契约、feature interface、Rust 大小及相关测试。Desktop handler 变化需要实际宿主编译／测试；catalog 合法性和 workspace 测试不替代它。仓库级变更按当前指南进行完整验证。
- 需要证明生成确定性时，在隔离环境重复生成并比较结果；检查命令通过不代表未知手写旁路不存在，也不代表生成器语义或所有权正确。临时增删演练清除其手写 fixture 后重新生成并确认干净，仅保留证据。
- 每条发现给出：严重程度、违反的原则、当前文件／行号、调用或所有权链、触发场景／影响、最小修正方向和验证条件。用 base 版本核对是新增回退、既有债务还是本 PR 已修复；缺乏证据的推断明确标为待验证。
- 报告同时说明已符合的重要链路、未覆盖范围、实际运行的命令和结果。检查通过与人工所有权审查结论分开，不能用静态审查宣称运行时已验证。
- Review 本身不授权修改产品代码、发布 PR 评论或提交／推送。

完成条件：读者能从固定版本、代码证据和测试结果复核结论，也能清楚看到尚未验证的部分。
